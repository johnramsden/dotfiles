Save a document to the Obsidian vault. Use when the user asks to write, add, or save an exploration, explanation, deep-dive, planning, or review document about: $ARGUMENTS

Follow these steps exactly:

1. Determine the repository name:
   - Run `git remote get-url origin 2>/dev/null | sed 's|.*/||; s|\.git$||'` to get it from git.
   - If that is empty, fall back to the basename of the current working directory.
   - If $ARGUMENTS contains an explicit repo name (e.g. "for ceph-csi"), use that instead.

2. Get today's date: run `date +%Y-%m-%d`. Also get the month: run `date +%Y-%m`.

3. Determine the document type from $ARGUMENTS or context, and map it to a subdirectory:
   - Exploration, explanation, deep-dive → `explanation/`
   - Planning, design, proposal → `planning/`
   - Review, audit, analysis → `reviews/`

4. Derive a short, descriptive kebab-case slug from the topic in $ARGUMENTS (e.g. "rados-object-lifecycle").

5. Construct the output path:
   ~/Canonical/Ceph/Docs/Ceph/repositories/<repo>/<subdir>/<YYYY-MM>/<YYYY-MM-DD>-<slug>.md

   Fallback to ~/Workspace/vault/repositories/<repo>/<subdir>/<YYYY-MM>/<YYYY-MM-DD>-<slug>.md if ~/Canonical doesnt exist.

6. Create the directory if it does not exist, then write the document there.

The document must follow these rules.

**Structure**

- Begin with a top-level `# Title` heading that matches the topic.
- Include a short introductory paragraph summarising the scope.
- Be organized into logical sections with `##` headings.
- Favour concrete detail, diagrams (as ASCII or Mermaid), and examples over vague prose.
- Use Markdown format.
- Not include a "Generated by Claude" footer or similar.

**Writing style — write for a beginner in the domain**

- Assume the reader is a competent software engineer who is **new to this domain** (Ceph, storage, Juju — whatever the topic is), reading months later with no memory of the conversation that produced the document. Never write for a fellow domain expert.
- Directly after the intro paragraph, add a `## Background` section (~100–150 words) before any technical detail. Answer in plain terms: what is this thing, why does it exist, and where does it fit in the bigger system. For very short documents, fold this into the intro instead.
- Open every section with one or two sentences on what it covers and why it matters — motivation before mechanism, every time.
- Expand every acronym at first use: `Full Term (ACRONYM)`. Define every domain-specific term at first use with a plain parenthetical of 15 words or fewer, e.g. "OSD (the daemon that stores data on one disk)". Define each term once — never re-explain it. Skip general software vocabulary the reader already knows (API, replication, database).
- If four or more domain terms appear, use a single `## Key Terms` section right after Background instead of inline parentheticals: one line per term, `**Term** — one-sentence plain definition`.
- Use simple words and short sentences: one idea per sentence, hard cap ~30 words — split anything longer. Paragraphs max 4 sentences; switch to bullets when listing more than 3 items. Active voice.
- Ground every major concept with exactly one device: a concrete example (command, snippet, sample output) or a single-sentence everyday analogy. Never stack analogies.
- Keep the document self-contained: never write "as discussed" or reference the conversation; briefly explain repo-internal file paths, function names, and project-specific terms at first mention.
- Stay concise: explanation ~800–1500 words, planning ~600–1200, review ~500–1000 (excluding code and diagrams). If over budget, cut repetition and filler first — never the Background section or the worked examples.

**Mermaid rules**

- In Mermaid graph node labels, use `<br>` for line breaks — never `\n` (Obsidian does not render `\n` inside node label strings).
- In Mermaid sequence diagram message labels and notes, use `<br/>` for line breaks — never `\n` or shell-style backslash continuation.
- In Mermaid, never put `(`, `)`, `{`, or `}` inside node labels, edge labels, participant aliases, or sequence message/note text — Mermaid treats them as shape/syntax delimiters and they break rendering in Obsidian even inside quoted strings. Rephrase using plain words, commas, or em dashes (e.g. `config 0,1,2` not `config {0,1,2}`; `leader 10.0.0.1` not `leader (10.0.0.1)`).
- In Mermaid, do not use `;` inside sequence-diagram message or note text — Mermaid treats `;` as a statement separator, so the message ends early and the rest becomes an invalid statement. Use a comma, period, or `<br/>` instead.

After writing the document, do a style pass before validating Mermaid: re-read the document as the target reader (an engineer new to this domain) and fix any sentence that assumes unstated knowledge; spot-check the three longest sentences against the 30-word cap; confirm every acronym is expanded at first use.

Then, you MUST truly validate every Mermaid block by rendering it with the real Mermaid parser — visual inspection and grepping are not sufficient (e.g. a stray `;` passes a grep but fails the parser). Run:

```
~/.claude/scripts/validate-mermaid.sh <path-to-the-document>
```

- This script extracts each ```mermaid block and renders it with `mmdc` (`@mermaid-js/mermaid-cli`), printing the exact parse error and line for any block that fails. It exits non-zero if any block is invalid.
- If `mmdc` is not installed, install it with `sudo snap install mermaid-cli` (provides `/snap/bin/mmdc`) or `npm install -g @mermaid-js/mermaid-cli`, then re-run.
- Gotcha: the snap build of `mmdc` is confined — it cannot read `/tmp` or hidden (dotfile) paths, only non-hidden paths under `$HOME`. The script already stages its work in a non-hidden `$HOME` dir to satisfy this.
- If any block fails, fix it and re-run the script until it reports PASS for every block (exit 0) before reporting the task done.
